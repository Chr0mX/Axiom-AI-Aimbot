# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Git Workflow

- **Main is branch-protected** — never push directly to `main`. Always develop on a feature branch and open a PR via `mcp__github__create_pull_request` targeting `chr0mx/axiom-ai-aimbot`.
- Branch naming convention in use: `claude/<topic>-<id>`
- After any rebase, re-author commits: `git config user.email noreply@anthropic.com && git config user.name Claude && git rebase --exec "git commit --amend --no-edit --reset-author" origin/main`

## Running Tests

```bash
# All tests
pytest tests/

# Single test file
pytest tests/test_inference.py

# Single test
pytest tests/test_config.py::TestConfigInit::test_screen_dimensions
```

Tests add `src/` to `sys.path` via `tests/conftest.py` — no install step needed.

**On non-Windows (e.g. this sandbox)**: this is fundamentally a Windows app — `pytest tests/` reports a large number of environment-only failures (missing `win32api`/PyQt6/pywin32, not code bugs); this baseline shifts as tests are added/removed, so when verifying a change doesn't regress anything, compare the failed/passed counts against a fresh baseline run rather than a hardcoded number. Any module with a top-level `import win32api` (or that transitively imports one, e.g. anything importing `win_utils`) fails at **collection**, not just at test-run time, which aborts the whole suite unless the import is deferred — the established pattern here is a pytest fixture (or an in-test `from ... import ...`) that does the import lazily, so a missing `win32api` fails just that file's tests individually instead of blocking every other test file's collection. `ai_loop.py`, `ai_aiming.py`, `auto_fire.py`, and `key_listener.py` all hit this (the first three via `win_utils`, `key_listener.py` directly); `ai_loop_utils.py` defers its `import win32api` inside a function, so it's collectible even though it still fails at test-run time. `app_controller.py` follows the same pattern (its `win_utils`/`onnxruntime`/`.ai_loop`/`.auto_fire`/`.session_utils` imports are all deferred inside the functions that need them), so `set_always_aim()` is testable here even though `start_ai_threads()` etc. still aren't callable. `detection_semantics.py`, `udp_receiver.py`, and `esp_server.py` don't hit either problem and are fully testable here.

## Architecture

### Entry Point
`src/main.py` — sets DPI awareness (`SetProcessDpiAwarenessContext` Per-Monitor V2 with fallbacks), injects `src/`, `src/python/dependencies/`, and PyWin32 paths into `sys.path`, pre-loads native DLLs, initialises logging, selects ONNX backend (DirectML / CUDA / TensorRT / CPU), then starts the Qt GUI.

`src/version.py` (`__version__`) is the single source of truth for the app version — read by `src/core/updater.py` (GitHub release check) and the About/version label in `other_page.py`; don't hardcode version strings elsewhere.

### Inference Pipeline (three threads)
The main loop (`src/core/ai_loop.py`, `ai_logic_loop()`) runs three concurrent workers:

1. **`_capture_worker`** — calls the active backend's `grab()` at `screenshot_interval`, writes frames into `capture_state['latest_frame']` under `frame_lock`. Also calls `set_preview_frame()` for the live preview panel. Hot-swaps capture backends every 0.5 s via `reinitialize_if_method_changed`.
2. **`_preprocess_worker`** — reads frames, letterboxes/resizes (or fast-path for square captures), builds the ONNX input tensor, pushes to `_tensor_queue`.
3. **Main inference thread** — pulls tensors, runs `model.run()` (or `run_with_iobinding()` for CUDA IO binding), calls `postprocess_outputs()` + NMS, then `process_aiming()`. Supports hot-swap of models and providers at runtime (`_try_hot_swap_model`).

Frame capture and inference are fully decoupled — capture backends must return `(H, W, 4)` uint8 BGRA.

### Screen Capture Backends (`src/core/screen_capture.py`)
Five backends share a common `grab(region) → np.ndarray | None` interface:
- **MSS** — GDI32, cross-platform fallback
- **dxcam** — Desktop Duplication API (GPU, lowest latency; returns `None` on no-change — caller reuses last valid frame)
- **UVCCapture** — OpenCV `VideoCapture` with a dedicated `_reader_thread` so `grab()` never blocks; supports probed FPS, MSMF/V4L2 backends, always-on-top pop-out preview. `uvc_capture_method == 'dshow'` additionally selects between two DirectShow implementations via `uvc_dshow_backend`: `'v1'` (default) is `cv2.VideoCapture(CAP_DSHOW)`; `'v2'` is the native `directshow_capture.dll` (`chr0mx/DirectShow-Capture-DLL`, vendored at `src/python/dependencies/`) via `src/core/dshow_capture_native.py`'s ctypes binding (`NativeDshowCapture`) — owns the capture graph's allocator/buffer count directly instead of going through OpenCV, for lower/OBS-like latency. Both MJPEG and NV12 are supported under v2 (`uvc_video_format`, restricted to those two in the GUI while v2 is active — `yuy2`/`yuv420p` have no v2 equivalent); MJPEG is decoded to BGR in `_reader_worker_native_dll`, NV12 reuses the same raw-NV12 crop-before-convert path (`_crop_nv12`) the cv2 path's `CAP_PROP_CONVERT_RGB` optimization already uses. `uvc_ffmpeg_enabled` (external `ffmpeg.exe` subprocess) is gated to `dshow` + `v1` only — ffmpeg has no MSMF demuxer on Windows, and v2 already owns the graph directly. `uvc_crop_mode == 'fixed'` (vs. the default `'dynamic'`, which recomputes the crop from the live Detection Range every frame) freezes a centered `detect_range_size` square as the capture region; on v2/NV12 this is requested as a genuine native crop via the DLL's `dsc_open_params.crop_x/y/width/height` (`_compute_fixed_uvc_crop_region()`, shared with the cv2 path) — **not** by asking the device to negotiate a smaller resolution, which carries no guarantee of being a spatial crop of the same framing rather than the whole scene rescaled. Device negotiation always requests the full `uvc_width`/`uvc_height` regardless of crop mode; the crop is a separate, later, in-DLL step. Because a DLL build predating this crop ABI addition silently ignores the trailing crop fields instead of rejecting them, `_init_native_dll` treats `capture_open()` succeeding as provisional, not proof — `_reader_worker_native_dll` confirms the crop actually took effect against the first real frame's delivered dimensions and self-heals to a software crop (`_fixed_region`) if the DLL didn't honor it. Native crop is NV12-only (MJPEG would need decode+crop+re-encode, which the DLL doesn't implement); MJPEG's fixed-crop mode always uses the software path.
- **NDICapture** — cyndilib frame-sync path (UYVY → BGRA via `cv2.COLOR_YUV2BGRA_UYVY`); uses buffer protocol (`np.frombuffer`) for zero-copy frame access; auto-reconnects on source loss
- **UdpCapture** — receives an MJPEG-over-UDP stream matching OBS's `udp_stream_filter` plugin wire format (`src/core/udp_receiver.py`: 14-byte chunk header, frame reassembly, stale-frame timeout); decodes JPEG chunks into BGRA frames

The module also owns the **live preview cell**: `set_preview_frame()` / `get_preview_frame()` / `set_preview_region()` / `get_preview_region()` expose the current detection-region frame to the GUI preview panel under a single `_preview_lock`.

### Config (`src/core/config.py`)
Single `Config` class — all runtime state lives here. Persistence is driven by `_FIELD_MAP`, a module-level dict mapping every flat `Config` attribute to its dotted path in the **v2 grouped JSON schema** (e.g. `'fov_size': 'aim.fov_size'`). `to_dict()` and `from_dict()` are both generated from `_FIELD_MAP`; adding a new persisted field only requires one entry there plus the `__init__` assignment.

**Three separate persistence targets:**
- `config.json` — all fields in `_FIELD_MAP` (v2 nested schema)
- `state.json` — one-time app state in `STATE_FIELDS` (`disclaimer_agreed`, `first_run_complete`, `ndi_installer_ran_once`)
- `language.json` — current UI language selection

`config_manager.py` owns load/save lifecycle, preset management, and migration from v1 flat format. Presets are full config snapshots saved as JSON to `config/*.json` (derived from `_FIELD_MAP`, so they can't drift from `Config`'s current field set); `src/core/presets/*.json` holds bundled built-in presets that get seeded into the user's `config/` dir on first run (never overwriting a same-named file the user already has). Preset names are sanitized (`_sanitize_config_name()`) before being interpolated into a file path — they can come from free-text GUI dialogs or an imported file's own `name` field, both untrusted.

**`ConfigManager.preview_config_changes(config_instance, config_name)`** — a dry run of `load_config()` used by `configs_page.py`'s Load button to show what a preset would actually change before applying it, instead of silently overwriting. Implemented as `copy.deepcopy(config_instance)` → `simulated.from_dict(preset_data)` (the exact code path a real load takes) → diff `_get_config_data()`'s output (the same flat, attr-keyed dict `save_config()`/`load_config()` already read and write) between the original and the simulated copy — so the preview can't drift from real load behavior, and needs no separate preset format of its own. Returns `[]` for "identical to current" (the GUI skips the confirmation prompt in that case and loads directly), `None` if the preset file couldn't be read (the GUI treats this the same as `load_config()` itself failing — falls through to the real call and lets its own error path report it), or a list of short change descriptions otherwise. `_describe_changed_attrs()` groups a handful of attrs that commonly change together (all 6 PID gains, every `makcu_*`/etc. field, `humanization`'s sub-fields) under one friendly "N values in `<group>`" line via a small prefix table (`_PRESET_DIFF_GROUPS`) — purely cosmetic, an attr missing from that table just falls back to its own prettified name instead of being grouped.

### Aiming & Anti-Recoil (`src/core/ai_aiming.py`)
`process_aiming()` is the per-frame entry point, called from `ai_loop.py` with the **full** FOV-filtered candidate list (never pre-reduced — see single-target note below). Key subsystems:
- **FOV filtering** (`filter_boxes_by_fov()`, `ai_loop_utils.py`) — the FOV is a rectangle by default (`fov_size` = width, `fov_height` = height; equal by default, i.e. a square), or an ellipse (a circle when width == height) with `fov_circle_filter_enabled` — `_ellipse_intersects_bbox()` does the ellipse/box test via an affine transform to a unit circle, shared verbatim by the in-game overlay's tracer-line/box-highlight passes (`overlay.py`), `screen_capture.py`'s `_draw_detection_overlay()` (the baked-into-the-frame preview annotations UVC/NDI/UDP fall back to, since the transparent Qt overlay can't render over those non-desktop sources the way it does for mss/dxcam — the one surface FOV-rectangle support originally missed, so a rectangular FOV visually looked square/circular for exactly those three backends even though the underlying filter was already correct), and the Web ESP client (`app.js`'s `ellipseIntersectsBbox()`, a hand-ported mirror since the browser can't import Python) so all four surfaces agree on what's "in FOV." `get_effective_detect_range_size()`/`_validate_detect_range_size()` clamp `detect_range_size`'s lower bound to `max(fov_size, fov_height)` so the (always-square) detection/capture region can contain the whole FOV rectangle, not just its width.
- **Reduce FOV on Active Target** (`fov_reduce_on_target_enabled`) — once a target is locked (`state.locked_box` non-`None`), `ai_loop_utils.compute_effective_fov()` shrinks both `fov_size` and `fov_height` to `fov_min_size_pct`% of their configured values (same percentage on each axis, so a rectangular/elliptical FOV keeps its aspect ratio while shrunk) for up to `fov_min_size_duration` seconds, so a random target entering the edge of the normally-larger FOV can't steal the lock mid-engagement. `state.fov_reduce_since` — the shrink window's start time — is set exactly once on the None→non-None edge of `locked_box`, not every frame a target stays locked (the same class of continuous-reset bug already fixed once for the MAKCU disengage delay: setting it unconditionally every frame would pin the elapsed time near zero forever and the duration could never expire). `fov_min_size_duration == 0` holds the shrink indefinitely while locked, matching this codebase's "0 = uncapped/off" convention elsewhere. Once the window *does* expire, `state.fov_reduce_expired` latches so the FOV stays at full size for the rest of the current lock — without it, "just expired" and "no window has ever started" are both indistinguishable states of `fov_reduce_since == 0.0` while `locked_box` is still non-`None`, so the very next frame would misread expiry as a fresh acquisition and re-arm the shrink immediately, producing an unbroken shrink/revert loop that (since the reverted frame lasts a single tick) looks exactly like the duration is never respected at all. `filter_boxes_by_fov()` takes an optional `fov_height` override parameter for this — the shrunk height for just this call, without touching `config.fov_height` itself (which must stay the user's real configured value). The FOV actually in effect this frame is published every frame (not just while shrunk) as the runtime-only `config.fov_effective_size`/`fov_effective_height` (unpersisted, same pattern as `uvc_actual_width`) so all four FOV-drawing surfaces (`overlay.py`, `screen_capture.py`'s `_draw_detection_overlay()`, the Web ESP snapshot) visually shrink the FOV circle/rectangle in sync with target selection, rather than always drawing the static configured size — the one exception is each surface's own detect-range-size floor, which deliberately still reads the full configured `fov_size`/`fov_height`, not the momentary shrunk value, since that floor is tied to the user's real setting.
- **Target selection** — `target_priority_mode` (`'distance'` / `'confidence'` / `'composite'`, weighted by `target_priority_confidence_weight`) scores candidates; shared logic lives in `find_closest_target()` (`ai_loop_utils.py`), used both by `process_aiming()` and the idle-detect path in `ai_loop.py`
- **Sticky lock** — IOU-based target persistence across short detection gaps (`sticky_lock_enabled`), with an adaptive IOU threshold that scales with FOV size (`_adaptive_sticky_iou`)
- **`state.locked_box` / `state.locked_confidence`** (`ai_loop_state.py`) — written on *every* successful selection regardless of `sticky_lock_enabled`, so other code (e.g. `single_target_mode`'s box-list reduction) can read back the real post-lock pick instead of re-deriving a lock-blind one
- **`single_target_mode`** — reduces the box list Web ESP/auto-fire/preview see to just the locked target. This reduction happens **after** `process_aiming()` runs, derived from `state.locked_box`; it must never pre-filter the candidate list before sticky lock sees it, or sticky lock can never win over the frame's raw priority winner
- **Motion prediction** (`prediction_enabled`) — `src/core/target_predictor.py` (`VelocityPredictor`) or `src/core/kalman_filter.py` (`KalmanFilter2D`, constant-velocity 2D); both `.reset()` on true target loss to avoid stale velocity carrying into a new target
- **Semantic false-positive filter** (`detect_semantic_filter_enabled`) — `src/core/detection_semantics.py`; three layers (ONNX class-name allow/deny lists, aspect-ratio geometry heuristics, min bbox size) to drop vegetation/vehicle/sign/HUD misdetections before target selection
- **PID controller** with separate X/Y axes (`pid_kp_x/y`, `pid_ki_x/y`, `pid_kd_x/y`). Nothing downstream clamps Kp — the GUI's P sliders just cap their travel at a proven-stable 0.0–0.5 band by default; `pid_unsafe_mode` re-maps that same slider travel to the full 0.0–1.0 range ("Unsafe Mode" toggle, Aim page)
- **Y-axis recoil suppression** (`aim_y_reduce_*`) — delay, ramp, floor, settle gate, and velocity restore
- **Humanization** — post-processes the final PID-output (dx, dy) delta only (never detection, PID state, or coordinate mapping) via `src/core/humanization.py` (`HumanizationConfig` dataclass, `apply_humanization()`). GUI (Aim page) exposes a master Enable + Intensity (0–100%, scales every effect) plus one on/off toggle per feature (Micro-Jitter, Motion Variation, Speed Shaping, Micro-Stutter, Reaction Variability) and a fine-tuning slider for each feature's underlying sub-parameter (jitter base/scale, variation range, speed-shaping thresholds/factor, stutter probability/bounds, reaction skip probability) — each sub-slider is shown (and enabled) only while both the master switch and its own feature toggle are on — hidden rather than greyed out, to keep an all-features-off view uncluttered. A "Reset to Defaults" button restores the entire block (including Intensity and all feature toggles) to `HumanizationConfig()`'s dataclass defaults. `Config.humanization` persists the whole dataclass as its own `"humanization"` JSON block (a plain dict round-trip via `dataclasses.asdict()`, separate from the normal dotted-path `_FIELD_MAP` schema everything else uses) — so any field is also hand-editable directly in `config.json`/presets even without a GUI control.
  - **Idle Micro-Jitter** (`micro_jitter_idle_enabled`, off by default) — `process_aiming()` (and therefore the rest of Humanization) only ever runs on frames where `is_aiming and boxes` in `ai_loop.py`, so holding the aim key with no target detected normally leaves the crosshair perfectly still. When this toggle is on, `ai_aiming.apply_idle_micro_jitter()` is called instead from `ai_loop.py`'s `else` branch (whenever `is_aiming` is still True that frame) and reuses `apply_humanization(0.0, 0.0, hcfg)` unchanged — Speed Shaping/Motion Variation/Micro-Stutter all no-op on a zero-magnitude input via their own `magnitude > 0.0` guards, so only Micro-Jitter's amplitude floor fires, going through the same `state.aim_carry_x/y` sub-pixel carry as the on-target path. Gated separately from `micro_jitter_enabled` (which only covers the on-target case), so it's a genuine opt-in with no behavior change for existing configs/presets.
- **Deadzone** — minimum pixel gap before movement fires
- **Sub-pixel carry** (`state.aim_carry_x/y`) — accumulates the fractional remainder integer truncation discards each frame, applied universally across all mouse backends so micro-corrections are never silently lost

Auto-fire (`src/core/auto_fire.py`) consumes `config.latest_boxes` (the single-target-reduced list when applicable) via `update_queues(...)`.

### Secondary / Weapon Detection (process-isolated)
Both run in a separate child process so the main inference loop and Qt UI are never blocked, feeding results back via a small "feeder" thread. Selected via `second_inference_mode` (`'off'` / `'v1_ocr'` / `'v2_onnx'`) — the Inference page shows/hides the ONNX confidence threshold accordingly.
- **`src/core/ocr_inference.py`** — PaddleOCR-based weapon-name reader
- **`src/core/hud_inference.py`** — YOLO11n ONNX weapon/attachment detector. ROI read from `config.hud_roi_coords` (`"x1,y1,x2,y2"`, default `"1490,953,1870,1041"`, Apex Legends HUD strip @ 1080p), 320×320 letterboxed input. Public API: `start(config)`, `stop()`, `trigger_hud_scan()`, `get_hud_results()`, `get_hud_roi_image()`

### Web ESP Overlay (`src/core/esp_server.py` + `src/web_overlay/`)
Optional LAN-accessible browser overlay (`web_esp_enabled`), modeled as "backend streams state, frontend draws it" — the PyQt in-game overlay stays the on-device renderer. Three daemon threads:
- **HTTP server** (stdlib `ThreadingHTTPServer`) serves the static client from `src/web_overlay/` (`index.html` / `app.js` / `styles.css`); bare `/` requests without a `?ws=` query 302-redirect to the actual bound WS port so the client never needs a manually-appended port
- **WebSocket server** — hand-rolled RFC 6455 (handshake + text-frame encoding, no external dependency), auto-increments the bind port on conflict (`_actual_ws_port`)
- **Broadcast loop** — ~`web_esp_fps` Hz, latest-state-wins; serializes a JSON snapshot of `Config` (`_build_snapshot()`) to all connected clients, including 1 Hz-computed `capture_fps`/`inference_fps`

Reads `config.latest_all_boxes` / `latest_all_confidences` (unreduced by `single_target_mode` — same set the in-game overlay draws), not `config.latest_boxes`, so the web view always shows every detection regardless of aiming mode.

### Web Control API (`src/core/app_controller.py` + `src/core/web_control_server.py` + `src/web_control_client/`)
A second, separate LAN server (`web_control_enabled`) — a **control plane**, not read-only telemetry like Web ESP above, so it's built on a different stack and a different trust model:
- **`app_controller.py`** — the shared application-logic boundary a Qt slot and a web route both call into. Plain functions, `config` first, no Qt import anywhere in the call chain (same tier as `ai_loop.py`/`config_manager.py`/`session_utils.py`). Holds `start_ai_threads()` / `stop_ai_threads()` / `pause_ai_inference()` / `resume_ai_inference()` — moved verbatim out of `main.py` (same behavior, same `_ai_threads_lock`) specifically so something other than `main.py`'s own startup/shutdown code can call them — and `set_always_aim(config, enabled)`, extracted from `keys_page.py`'s `_onAlwaysAimChanged` (which used to inline the `always_aim`/`idle_detect_enabled` coupled write directly in a Qt slot; the decide-half now lives here, the slot just calls it then refreshes its own widgets). Also holds `connect_makcu(config)` / `disconnect_makcu(config)` — thin wrappers around `win_utils.makcu_mouse`'s already GUI-free, already lock-safe-off-the-GUI-thread `connect_makcu()`/`disconnect_makcu()`; the wrappers exist only to read `config.makcu_com_port`/`makcu_baud_rate` (in place of `keys_page.py`'s combo boxes, which a web caller doesn't have) and to guard against an empty/unconfigured port, not to add new hardware logic. Every heavy import (`win_utils`/`onnxruntime`/`.ai_loop`/`.auto_fire`/`.session_utils`) is deferred inside each function body rather than at module top level — same reasoning as `ai_loop_utils.py`'s deferred `win32api` import — so the module itself (and anything that only needs e.g. `set_always_aim`) stays importable on a machine without those packages.
- **A module-level `_multi_field_lock`** in `app_controller.py` guards only *multi-field* Config writes (currently just `set_always_aim`'s coupled pair) — ordinary single-field `setattr` elsewhere in this codebase stays unlocked, relying on the GIL for atomicity, unchanged. Deliberately a module-level lock, not a `Config` attribute: `ConfigManager.preview_config_changes()`'s `copy.deepcopy(config_instance)` raises `TypeError: cannot pickle '_thread.lock' object` on a raw `threading.Lock` instance attribute — confirmed directly — so a lock must never live on `Config` itself. A second, separate module-level `_makcu_connect_lock` guards only `connect_makcu()`, serializing two overlapping connect attempts racing on the same port (e.g. the Qt GUI and a web client both clicking connect within the same handshake window) — `disconnect_makcu()` needs no lock, its teardown path is idempotent-safe.
- **`web_control_server.py`** — FastAPI + uvicorn (not the stdlib approach `esp_server.py` uses): a control-plane server needs real request validation and inbound-frame handling that hand-rolled RFC 6455 (push-only, never parses a client frame) doesn't provide. Runs uvicorn's ASGI server inside this process on its own background thread (`_ThreadServer`, a `uvicorn.Server` subclass with `install_signal_handlers()` overridden to a no-op — installing signal handlers only works on the main thread). Every route requires a shared token via the `X-Axiom-Token` header (`config.web_control_token`, auto-generated with `secrets.token_urlsafe(24)` the first time the feature is enabled and empty) checked by a FastAPI dependency — unlike Web ESP's explicitly-documented no-auth posture, this server can mutate state, so it can't reuse that stance. `GET /api/status` returns a smaller, control-oriented field set (aim state, model, FPS, MAKCU connection + port) — not a reuse of `esp_server._build_snapshot()`. Control actions so far: `POST /api/control/always_aim` (calling `app_controller.set_always_aim()`) and `POST /api/control/makcu_connect` / `POST /api/control/makcu_disconnect` (calling the `app_controller` MAKCU wrappers). A failed MAKCU connect (bad/unset port, failed handshake) is a normal runtime outcome, not a request error, so it comes back as HTTP 200 with `{"ok": false, "reason": "no_port_configured"|"connect_failed"}` rather than an error status — HTTP error codes stay reserved for the auth/validation layer (401 bad token, 422 malformed body). `fastapi`/`uvicorn` are vendored straight into `src/python/dependencies/` — the same tracked-in-git directory `main.py` already puts on `sys.path` unconditionally at startup, alongside `qfluentwidgets`/`vgamepad`/`pywin32`/`directshow_capture.dll` — rather than installed on demand via a separate script, so no first-run install step is needed. Every import of them in `web_control_server.py` is still deferred inside `start()` rather than at module top level, so the module stays importable (and `start()` fails soft — logs and returns `False`) on a checkout that predates them being vendored in, the same way `main.py` already wraps `esp_server.start()` in a try/except.
- **`src/web_control_client/`** — sibling to `src/web_overlay/`, same plain HTML/JS/CSS style (no framework, no build step). Polls `GET /api/status` every second, shows an Always-Aim toggle wired to `POST /api/control/always_aim` and a MAKCU Connect toggle wired to the two MAKCU routes — the latter's `change` handler reverts the toggle both on a transport-level failure (`!res.ok`) and on a normal `200 {"ok": false}` body, unlike the always_aim toggle (which can't fail that second way). The access token is entered once and kept in that page's own `localStorage` — never sent anywhere except the `X-Axiom-Token` header on each request.
- **GUI wiring** — a "Remote Control" `SettingCardGroup` on `other_page.py` (Enable switch, port field with the same 600ms-debounced restart-on-change pattern as Web ESP's `visuals_page.py`, a token display with Copy/Regenerate buttons, an "Open in browser" button). Separately, `other_page.py`'s own MAKCU Hardware status (`_makcuHwTimer`, 3s) already re-queries `is_makcu_connected()` live on every tick, so it picks up a web-triggered connect/disconnect for free; `keys_page.py`'s Connect/Disconnect button did not — its status refresh only ran from four page-local event sites — so `_updateMakcuAimStatus()` (its one recurring 50ms timer) now also compares against `self._isMakcuConnected` and refreshes the button/label on a mismatch, closing that gap without adding new polling infrastructure.
- **Rollout is intentionally incremental** — `always_aim` is the first control action because it already had a real GUI checkbox with a well-understood side effect, exercising the full stack (auth → route → `app_controller` → `Config` → Qt reflection) at minimum risk. MAKCU connect/disconnect followed as the next-smallest slice, since `win_utils.makcu_mouse` was already GUI-free with nothing to extract. Model/provider switching and AI start/stop remain — the `app_controller` functions for AI start/stop already exist but need `main.py`'s capture/overlay queues threaded into `web_control_server.start()` first; model switching still needs a new decide function that explicitly refuses (rather than GUI-redirects) a TensorRT build or DirectML restart, since a web route can't trigger either headlessly.

### In-Game Overlay & Status Panel (`src/gui/`)
The actual on-device renderer referenced above — plain PyQt widgets, not part of `fluent_app/`:
- **`overlay.py`** — transparent, click-through `QWidget` drawing FOV/detect-range circles, detection boxes, confidence text, tracer lines, and the aim-point X marker directly over the game window. Colors go through the `OverlayColors` static-method wrapper (`get_fov_color()`, `get_box_color()`, `get_tracer_color()`, `get_aim_marker_color()`, etc.), each backed by a `ThemeColors.OVERLAY_*` entry — never hardcode a color here directly, add a new `ThemeColors` entry and getter instead. `box_color_theme` can override the detect-box color with a named preset instead of the theme default.
- **`status_panel.py`** — the on-screen status HUD (aim state, FPS, model name, MAKCU/Xbox connection). Supports Windows Acrylic blur via the legacy `SetWindowCompositionAttribute` API; re-reads language strings on its own refresh timer rather than needing a `retranslateUi()` call.

### Other Standalone Dev Tools (`src/core/`)
Not wired into the GUI or main loop; run directly for diagnosis/tuning.
- **`obs_inspect_filters.py`** — read-only OBS WebSocket inspector (`python src/core/obs_inspect_filters.py --source "Your Source Name"`). Connects to OBS's built-in WebSocket server (port 4455) and dumps every filter's full settings dict for a given source — used to check whether `udp_stream_filter` (or any other filter) exposes its own resolution/scale/quality setting without hunting through the OBS UI by hand. Never modifies OBS state. `--list-sources` enumerates sources if you don't know the exact name.
- **`bench_udp.py`** / **`_bench_udp_sender.py`** — standalone UDP receive-pipeline benchmark for the `UdpCapture` backend (`python src/core/bench_udp.py decode-bench|loopback-bench ...`). Isolates whether a low observed FPS is real packet loss (`live` mode, watch `dropped_fps`), JPEG decode CPU cost (`decode-bench`, measures the `cv2.imdecode` ceiling with no networking), or raw UDP-assembly throughput (`loopback-bench`, spins up a real `UdpJpegReceiver` on `127.0.0.1` and fires synthetic frames at it from `_bench_udp_sender.py` — a genuinely separate OS process, not a thread, so it doesn't share a GIL with the receiver, matching the real deployment where the OBS sender is an independent process).

### Mouse/Device Backends (`src/win_utils/`)
All backends expose `send_mouse_move_<method>(dx, dy)` and `send_mouse_click_<method>()`. Selected at runtime from `config.mouse_move_method`. Methods:
- `sendinput` / `mouse_event` — Windows `SendInput` / `mouse_event` API
- `makcu` — MAKCU USB HID device at 4 Mbaud (`_OPERATING_BAUD`), ASCII protocol; see `docs/MAKCU_Native_API.md` for the wire protocol reference. `move()` and `click()` must never hold `self._lock` across a `time.sleep()` — lock must be released before any sleep. Scroll-wheel input excluded from aim-button detection (masked to bits 0-4, `_BTN_BITS`). Self-healing: a background reconnect-watchdog thread retries the connection automatically on USB glitches. MAKCU click state is reported to `status_panel.py` via a dedicated callback. `makcu_mouse_binary.py` (the V2 binary-protocol variant) is unused in production today — kept in place for a future MAKCU firmware version; don't wire it in without first fixing the lock-across-sleep violation in its `connect()`/`_send_cmd()`.
- `arduino` — Arduino Leonardo HID (`arduino_mouse.py`, `arduino_spoofer.py`)
- `ddxoft` — ddxoft driver (`ddxoft_mouse.py`)
- `xbox` — Virtual Xbox 360 controller via ViGEmBus (`xbox_controller.py`, `gamepad_input.py`)

Each page extends `BasePage` and calls `setConfig(config)` to bind to the live `Config` object. Shared widget primitives live in `fluent_app/components/slider_spin_card.py` (`SliderLabelCard`, `SliderDoubleSpinCard`).

`window.py` also mounts a **`CapturePreviewPanel`** (`fluent_app/components/capture_preview.py`) as a collapsible side panel with a `◀` arrow toggle; the panel polls `screen_capture.get_preview_frame()` and displays a live feed with FPS counter and pop-out support.

**Keys page hotkey conflict warning** — `keyConflictCard`, a `SettingCard` banner at the top of `keys_page.py`, hidden unless `_checkKeyConflicts()` finds a genuinely confusing hotkey setup. It deliberately does **not** flag every pair of slots sharing a VK: `_collectKeySlotGroups()` groups slots by *purpose* (the 3 Aim Keys together, the 2 Auto-Fire keys together; in MAKCU mode, Inference and Auto Aim Key are each their own single-item group) and only two things get flagged — a redundant duplicate *within* one group (e.g. Aim Key 1 == Aim Key 2, wastes a slot, almost certainly accidental), and the edge-triggered toggle key (`aim_toggle_key`, flips `AimToggle` on press — see `key_listener.py`) landing on the same VK as any hold-based key (pressing it then also reads as "held" for whatever else has it, and can flip the toggle back off mid-hold). Binding an Aim Key and an Auto-Fire key — or, in MAKCU mode, the Inference and Auto Aim Key buttons — to the *same* button is deliberately never flagged: that's a common, often-intentional "hold one button to do both" setup, and it's this app's own shipped default (`AimKeys[1]` and `auto_fire_key` are both Mouse X2 out of the box), so cross-purpose overlap being flagged would make every fresh install show a false-positive warning. Slot reachability mirrors `_updateMakcuVisibility()`/`_refreshMakcuVisibility()` exactly (a card hidden by mode/`always_aim`/`keep_detecting` is excluded from the scan), and the scan re-runs after every rebind, mode switch, and `retranslateUi()`.

**Theming** (`fluent_app/theme_colors.py`) — a single `ThemeColors` class of `ColorPair`/`ColorPairWithAlpha` descriptors (`.get()` returns a CSS color string, `.qcolor()` a `QColor`), each with light/dark defaults and an optional override from a user `theme_colors.json`. `isDarkTheme()` (qfluentwidgets) picks which side of the pair applies. Any `setStyleSheet(...)` call with a literal hex/rgb color instead of a `ThemeColors.*.get()` reference is a theming bug — it won't adapt to a light/dark toggle. (`theme_manager.py`, a separate unused QSS-generator module, was deleted as dead code — it was never invoked anywhere.)

**First-run flow**: `fluent_app/setup_wizard.py` (Welcome → Language → Theme → Acrylic → Performance → Done, gated on `state.json`'s `first_run_complete`) followed by `gui/disclaimer_dialog.py` (gated on `disclaimer_agreed`; body text loaded from a single English-only `Disclaimer.md`, deliberately not localized — translating just the button chrome around a permanently-English legal document would be a confusing half-measure). The wizard tracks its own in-progress theme preview (`self._isDark`) separately from the app's real theme — `setTheme()` isn't actually called until the wizard closes (`applyChosenTheme()`, invoked from `main.py`), so any wizard-page widget that needs to look right in both previews must read the wizard's own state, not `isDarkTheme()`.

**i18n**: `t(key, default)` (`fluent_app/language_manager.py`) looks up `key` in the active language's JSON (`src/core/language_data/*.json`, 10 languages) and falls back to `default` (always English) if the key is missing — a missing key never crashes or shows blank, just shows English regardless of the selected language. Widgets built with a `t()`-wrapped title/description at construction must have the *same* call repeated inside that page's `retranslateUi()` (called from `window.py`'s `_refreshUI()` on every language switch) or the text goes stale after the first switch — this has been a recurring bug source; when adding a new card/label, grep an existing correct one in the same file for the exact `titleLabel`/`contentLabel` API before wiring a new one in. Translation completeness varies — English has the most keys (~290); other languages are missing anywhere from ~20 to ~75 of them (pre-existing, not something a single pass has closed).

### ONNX / TensorRT
Models go in `Model/` (`Model_Hud/` for the secondary weapon-detector model). The preprocess fast-path is automatic and backend-agnostic, driven purely by the captured frame's own shape (not a config flag): an exact `model_input_size × model_input_size` frame skips resize/letterbox entirely (`preprocess_image()`, `inference.py`); a square-but-different-size frame gets a plain nearest-neighbor resize with no padding (`fast_resize`, derived in `ai_loop.py` from `frame.shape[0] == frame.shape[1]`); only a non-square frame gets a real letterbox with padding. TensorRT engines are built by `src/core/convert_to_engine.py` and cached in `trt_cache/` at the project root (`session_utils.py`'s `_TRT_CACHE_DIR`) — **not** `%LOCALAPPDATA%\AxiomAI\`, which is only where the TensorRT *pip package itself* gets installed by `Install TensorRT.bat`, a separate concern. `cuda_io_binding_enabled` enables zero-copy CUDA inference (CUDA provider only).

Both `model_page.py` and `convert_page.py` pair their model `ComboBox` with a `SearchLineEdit` (`modelSearchEdit`) that live-filters the combo by case-insensitive filename substring as the user types — a plain filter, not an editable combo, so there's no way to type-and-Enter a phantom entry that doesn't correspond to a real `.onnx` file. Each page keeps its own master file list (`self._all_model_files`, refreshed by `_refreshModelList()`) and re-derives the combo's visible subset from it in `_onModelSearchChanged()`, which always keeps whatever's currently selected in the list even if the search text doesn't match it — so narrowing the search can never make the combo appear to show the wrong "currently active" model.

**A model with no cached `.engine` yet is a 1-5 minute *synchronous* build** the first time `onnxruntime.InferenceSession(...)` is created with the TensorRT provider — never let that call happen inline on `ai_loop.py`'s hot-swap path (`_try_hot_swap_model()`, called once per frame on the main inference thread), or the whole aim loop freezes with no progress feedback for the duration. Two layers guard against this:
- **GUI (`model_page.py`)** — before ever writing a model/backend combination to `config` that would make TensorRT the effective provider, `_redirectToConvertIfNeeded()` calls `session_utils.needs_trt_build(config, model_path)`; if true, it switches the window to the Convert tab (`FluentWindow.switchTo()`) and calls `ConvertPage.startConversionFor(model_path)` — the same background-thread + progress-bar build the Convert tab's own button uses — instead of ever setting `config.model_path`/`config.inference_backend` to that combination. `ConvertPage._onConvertFinished()` applies `config.model_path` to the just-built model on success and calls `window._refreshAllPages()`, so the app picks it up automatically (now a near-instant cache hit) without the user re-selecting it. This is wired into both the model combo (`_onModelChanged`) and the backend combo (`_onInferenceBackendChanged`, for the non-restart transitions — DirectML↔other still goes through the existing app-restart flow, which is a separate first-load path this doesn't cover).
- **`ai_loop.py`'s `_try_hot_swap_model()`** — a safety net for anything that bypasses the GUI (a loaded preset, a hand-edited `config.json`): `session_utils.needs_trt_build()` is checked before the `InferenceSession(...)` call; if a build would be needed, the swap is skipped (current model kept running, no freeze) and a warning is logged instead.

`session_utils.find_trt_engine_cache(model_path)` is the shared existence check (mirrors `build_provider_list()`'s `trt_engine_cache_prefix` = model filename stem convention); `effective_first_provider(config)` answers "is TensorRT actually what this config would try first" without duplicating `build_provider_list()`'s auto/backend-selection logic; `needs_trt_build()` combines both.

`model_page.py`'s model combo also surfaces cache status per-entry, before the user even opens the dropdown: `_applyModelBadges()` icons each item ✓ (`FluentIcon.ACCEPT`, cached) or ⬇ (`FluentIcon.CLOUD_DOWNLOAD`, would trigger the 1-5 min build above) via `setItemIcon()` — this only changes the item's icon, never its `.text`, so it can't interfere with the plain-filename string matching the rest of the page relies on (`_onModelChanged`'s `os.path.join("Model", text)`, the search filter's basename comparisons, etc.). `_isTensorRtActive()` (reuses `effective_first_provider()`) hides the badges entirely when TensorRT isn't the active backend, since cache status is meaningless noise under any other provider — a `modelCard` subtitle legend explaining the icons is shown/hidden the same way. Cache status itself (`_model_engine_cached`, one `find_trt_engine_cache()` call per model) is recomputed by `_refreshModelList()`; badge/legend *visibility* is also re-applied on every inference-backend change (`_onInferenceBackendChanged`) and by `_onModelSearchChanged()`'s combo rebuild, without re-scanning disk.
